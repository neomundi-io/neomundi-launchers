# 🇫🇷 Français

## Infrastructure minimale. Valeur maximale.

NeoMundi est né d’une intuition simple et d’une question presque philosophique :

**comment un système intelligent peut-il continuer à fonctionner, s’adapter et durer sans dériver indéfiniment ni mobiliser toujours davantage de ressources pour maintenir sa cohérence ?**

Cette intuition a progressivement conduit à une approche biomimétique.

Les systèmes vivants ne maintiennent pas leur équilibre en supprimant toute variation. Ils évoluent à l’intérieur de régimes dynamiques où stabilité, adaptation, dépense énergétique et régulation restent continuellement liées.

Appliquée aux systèmes d’intelligence artificielle, cette intuition conduit à une idée simple : avant de vouloir réguler un système, il faut pouvoir observer son état.

NeoMundi cherche ainsi à instrumenter certains phénomènes associés à la stabilité, à la variation et à la dérive comportementale des systèmes d’IA en fonctionnement.

L’objectif est de rendre observable un espace dans lequel peuvent émerger les conditions d’une **régulation** et, à terme, d’une forme d’**homéostasie computationnelle**.

Il ne s’agit pas d’imposer artificiellement un équilibre.

Il s’agit d’abord de pouvoir mesurer les conditions dans lesquelles un système demeure relativement stable, change de régime ou dérive.

Cette approche scientifique conduit naturellement à une philosophie d’ingénierie.

Si une fonction essentielle peut être rendue accessible par une infrastructure légère, il n’existe aucune raison de commencer par construire une architecture inutilement lourde.

C’est dans cette continuité que NeoMundi explore une approche que nous appelons :

# Arte Povera Software

---

## Construire moins, mais construire juste.

Le logiciel moderne accumule facilement :

- les couches ;
- les dépendances ;
- les frameworks ;
- les interfaces ;
- les abstractions ;
- les abonnements ;
- les infrastructures ;
- les composants intermédiaires.

Cette accumulation peut parfois être nécessaire.

Mais elle peut également devenir une fin en soi.

Nous choisissons une autre voie.

**Construire moins, mais construire juste.**

Une page peut appeler plusieurs scripts, modèles, API et protocoles.

Un launcher de quelques fichiers peut ouvrir l’accès à une infrastructure de mesure beaucoup plus profonde.

Un simple fichier texte peut devenir le point d’entrée d’une campagne expérimentale.

Une interface minimale peut permettre d’utiliser une fonction complexe sans obliger l’utilisateur à comprendre toute l’architecture qui la produit.

La simplicité visible n’est pas nécessairement le signe d’une technologie simple.

Elle peut être le résultat d’un effort de conception.

---

## Chaque couche doit justifier son existence.

Nous commençons par les composants nécessaires pour rendre un usage possible.

Chaque nouvelle couche doit ensuite démontrer la valeur qu’elle apporte avant d’être ajoutée.

Nous privilégions :

- l’usage avant la plateforme ;
- la preuve avant la promesse ;
- les briques légères avant le monolithe ;
- l’expérimentation avant l’industrialisation prématurée ;
- la documentation réelle avant la fiction industrielle ;
- l’interopérabilité avant l’enfermement ;
- la sobriété avant la sophistication inutile.

Une infrastructure n’est pas meilleure parce qu’elle possède davantage de composants.

Elle devient meilleure lorsque chaque composant répond à une nécessité démontrée.

---

## La complexité peut rester sous une surface simple.

Arte Povera Software ne consiste pas à nier la complexité.

NeoMundi travaille précisément sur des phénomènes qui peuvent être complexes :

- variabilité comportementale ;
- stabilité ;
- dérive ;
- transitions ;
- mesure runtime ;
- reproductibilité ;
- interopérabilité ;
- gouvernance.

La complexité scientifique peut rester profonde.

La complexité technique peut être réelle.

Ce que nous cherchons à éviter est la transformation automatique de cette profondeur en complexité inutile pour l’utilisateur.

Un utilisateur ne devrait pas avoir besoin de comprendre l’ensemble d’une infrastructure pour pouvoir utiliser une mesure.

La profondeur de l’instrument et la simplicité de son utilisation ne sont pas contradictoires.

---

## Commencer par l’instrument.

Dans une approche classique, une nouvelle fonction conduit rapidement à vouloir construire :

```text
une plateforme
+
un dashboard
+
une interface
+
un système de comptes
+
une nouvelle base de données
+
un nouveau workflow
+
une nouvelle couche d’orchestration
```

Arte Povera Software pose d’abord une autre question :

**quelle est la quantité minimale d’infrastructure nécessaire pour rendre cette fonction réellement utilisable ?**

La réponse peut parfois être :

```text
un fichier
+
un script
+
une API
```

Si cela suffit pour tester l’usage, produire une preuve et apprendre, cela peut être le bon point de départ.

L’infrastructure supplémentaire viendra lorsque l’usage démontrera qu’elle est nécessaire.

---

## Mesurer avant d’industrialiser.

Une idée n’a pas nécessairement besoin d’une plateforme.

Elle a besoin d’être testée.

Un usage n’a pas nécessairement besoin d’une infrastructure industrielle.

Il a d’abord besoin de produire une preuve.

Un prototype utile peut révéler davantage qu’une architecture ambitieuse construite avant d’avoir rencontré ses utilisateurs.

Nous cherchons donc à progresser par étapes :

```text
intuition
↓
instrument minimal
↓
expérience
↓
mesure
↓
preuve
↓
usage
↓
industrialisation lorsque nécessaire
```

Cette séquence permet de concentrer les ressources là où elles deviennent réellement utiles.

---

## Ouvrir ce qui doit circuler.

Open source ne signifie pas absence de modèle économique.

Toutes les couches d’un système n’ont pas nécessairement besoin d’avoir le même degré d’ouverture.

Des launchers, interfaces, exemples, connecteurs ou composants destinés à faciliter :

- l’expérimentation ;
- l’intégration ;
- l’interopérabilité ;
- la reproductibilité ;
- l’usage ;

peuvent être ouverts lorsque cette ouverture augmente leur utilité.

La valeur économique peut ensuite se construire autour de nombreuses dimensions :

- l’exécution ;
- la mesure ;
- l’échelle ;
- l’intégration ;
- la disponibilité ;
- la conformité ;
- l’interprétation ;
- l’exploitation opérationnelle ;
- les services ;
- la responsabilité ;
- les infrastructures nécessaires au passage à l’échelle.

Nous ne sommes pas anti-SaaS.

Nous ne sommes pas anti-plateforme.

Nous sommes **anti-complexité inutile**.

---

## Une mesure fondamentale peut alimenter de nombreux usages.

NeoMundi développe une couche de mesure runtime destinée à observer certains comportements des systèmes d’intelligence artificielle.

Une mesure fondamentale n’a pas besoin d’être confondue avec tous les usages qui peuvent en dériver.

Autour d’une même couche de mesure peuvent se construire :

- des launchers ;
- des workflows ;
- des outils de reporting ;
- des visualisations ;
- des connecteurs ;
- des systèmes de gouvernance ;
- des expériences scientifiques ;
- des outils métier ;
- des infrastructures spécialisées ;
- des articulations avec des systèmes tiers.

Ces objets peuvent avoir des tailles, des fonctions et des niveaux de sophistication extrêmement différents.

Certains peuvent rester très petits.

D’autres pourront devenir des systèmes industriels importants.

La fonction d’Arte Povera Software n’est pas d’empêcher cette évolution.

Elle consiste à **ne pas la précipiter**.

---

## Des launchers avant une bibliothèque de plateformes.

Un launcher est une forme particulièrement simple de logiciel.

Il peut :

- prendre un fichier ;
- appeler un service ;
- exécuter une série d’actions ;
- appliquer quelques paramètres ;
- produire un résultat.

Il peut parfois tenir dans quelques fichiers seulement.

C’est précisément ce qui le rend intéressant.

Un launcher permet de rendre une fonction immédiatement testable sans construire prématurément une plateforme complète autour d’elle.

Plusieurs launchers peuvent ensuite faire apparaître :

- des usages récurrents ;
- des composants communs ;
- des besoins partagés ;
- des fonctions qui méritent d’être industrialisées.

L’architecture peut ainsi émerger de l’usage au lieu d’être entièrement décrétée avant lui.

---

## Reporting léger.

La même logique s’applique aux sorties.

Un résultat n’a pas nécessairement besoin d’un dashboard permanent.

Une bibliothèque légère peut transformer des données en :

```text
CSV
HTML
JSON
graphiques
tableaux
résumés
comparaisons longitudinales
rapports
```

Lorsque quelques scripts Python suffisent à répondre à un besoin, ils peuvent constituer la bonne solution.

Si l’usage devient récurrent, collaboratif ou critique, une infrastructure plus importante pourra ensuite être construite.

---

## AI Periscope : un premier artefact.

**NeoMundi AI Periscope v0.1.0** constitue une première matérialisation volontairement simple de cette approche.

Son principe est minimal :

```text
Votre dataset
      ↓
AI Periscope
      ↓
NeoMundi ControlTower
      ↓
Votre provider
      ↓
Votre modèle
      ↓
Mesure runtime
```

L’utilisateur choisit :

- son provider ;
- son modèle ;
- son fichier de prompts ;
- son nombre de répétitions ;
- ses paramètres expérimentaux.

AI Periscope ne cherche pas à devenir une nouvelle plateforme.

Il ajoute uniquement le chemin nécessaire entre une expérience définie par l’utilisateur et la couche de mesure NeoMundi.

Pas de dataset imposé.

Pas de benchmark imposé.

Pas de nouvelle interface obligatoire.

Pas de protocole métier imposé.

**Juste ce qui manque pour rendre l’expérience possible.**

---

## Infrastructure minimale ne signifie pas ambition minimale.

Notre ambition n’est pas petite.

Nos moyens sont concentrés.

Une infrastructure peut commencer petite tout en poursuivant une ambition importante.

Le rôle d’une architecture initiale n’est pas de reproduire dès le premier jour la forme qu’elle pourrait avoir plusieurs années plus tard.

Son rôle est de rendre possible la prochaine étape.

Nous cherchons donc à construire des systèmes :

- suffisamment simples pour être testés ;
- suffisamment clairs pour être compris ;
- suffisamment documentés pour être reproduits ;
- suffisamment ouverts pour être intégrés lorsque cela est utile ;
- suffisamment robustes pour produire de vraies observations ;
- suffisamment mesurables pour évoluer sur la base de preuves.

L’industrialisation vient lorsque l’usage la justifie.

---

## Une architecture qui peut émerger.

Arte Povera Software n’est pas une esthétique du logiciel pauvre.

Ce n’est pas la recherche du code le plus court.

Ce n’est pas un refus de l’ingénierie industrielle.

C’est une discipline de progression.

Elle accepte qu’un système puisse commencer par :

```text
un script
```

puis devenir :

```text
une bibliothèque
```

puis :

```text
un service
```

puis éventuellement :

```text
une infrastructure
```

si chaque transition répond à un besoin réel.

L’architecture n’est donc pas nécessairement entièrement connue au commencement.

Une partie de l’architecture peut émerger de la confrontation entre :

- la mesure ;
- l’usage ;
- les utilisateurs ;
- les contraintes ;
- les preuves.

# 🇬🇧 English

## Minimal infrastructure. Maximum value.

NeoMundi emerged from a simple intuition and an almost philosophical question:

**how can an intelligent system continue to operate, adapt and endure without drifting indefinitely or requiring ever-increasing resources simply to maintain coherence?**

This intuition gradually led to a biomimetic approach.

Living systems do not maintain equilibrium by eliminating all variation. They evolve within dynamic regimes in which stability, adaptation, energy expenditure and regulation remain continuously connected.

Applied to artificial intelligence systems, this intuition leads to a simple idea: before attempting to regulate a system, we first need to observe its state.

NeoMundi therefore seeks to instrument phenomena associated with the stability, variation and behavioral drift of AI systems at runtime.

The objective is to make observable a space in which the conditions for **regulation** and, ultimately, a form of **computational homeostasis** may emerge.

The goal is not to artificially impose equilibrium.

The first requirement is to measure the conditions under which a system remains relatively stable, changes regime or begins to drift.

This scientific approach naturally leads to an engineering philosophy.

If an essential function can be made accessible through lightweight infrastructure, there is no reason to begin by building an unnecessarily heavy architecture.

It is within this continuity that NeoMundi explores an approach we call:

# Arte Povera Software

---

## Build less, but build what is needed.

Modern software easily accumulates:

- layers;
- dependencies;
- frameworks;
- interfaces;
- abstractions;
- subscriptions;
- infrastructure;
- intermediary components.

This accumulation may sometimes be necessary.

But it can also become an objective in itself.

We choose another path.

**Build less, but build what is needed.**

A single page can call multiple scripts, models, APIs and protocols.

A launcher made of only a few files can provide access to a much deeper measurement infrastructure.

A simple text file can become the entry point for an experimental campaign.

A minimal interface can make a complex function usable without forcing the user to understand the entire architecture behind it.

Visible simplicity is not necessarily evidence of simple technology.

It may be the result of deliberate design.

---

## Every layer must justify its existence.

We begin with the components required to make an actual use possible.

Every additional layer must then demonstrate the value it brings before it is added.

We favor:

- use before platform;
- evidence before promise;
- lightweight components before monoliths;
- experimentation before premature industrialization;
- real documentation before industrial fiction;
- interoperability before lock-in;
- sobriety before unnecessary sophistication.

Infrastructure does not become better simply because it contains more components.

It becomes better when every component answers a demonstrated need.

---

## Complexity can remain beneath a simple surface.

Arte Povera Software does not mean denying complexity.

NeoMundi works precisely with phenomena that can be complex:

- behavioral variability;
- stability;
- drift;
- transitions;
- runtime measurement;
- reproducibility;
- interoperability;
- governance.

Scientific complexity can remain deep.

Technical complexity can be real.

What we seek to avoid is automatically translating that depth into unnecessary complexity for the user.

A user should not need to understand an entire infrastructure in order to use a measurement.

The depth of an instrument and the simplicity of its use are not contradictory.

---

## Begin with the instrument.

In a conventional approach, a new function can quickly lead to building:

```text
a platform
+
a dashboard
+
an interface
+
an account system
+
a new database
+
a new workflow
+
a new orchestration layer
```

Arte Povera Software begins with another question:

**what is the minimum amount of infrastructure required to make this function genuinely usable?**

Sometimes the answer may be:

```text
one file
+
one script
+
one API
```

If this is enough to test the use, produce evidence and learn, it may be the correct starting point.

Additional infrastructure can come when actual use demonstrates that it is needed.

---

## Measure before industrializing.

An idea does not necessarily need a platform.

It needs to be tested.

A use case does not necessarily need industrial infrastructure.

It first needs to produce evidence.

A useful prototype can reveal more than an ambitious architecture built before encountering its users.

We therefore seek to progress through stages:

```text
intuition
↓
minimal instrument
↓
experiment
↓
measurement
↓
evidence
↓
use
↓
industrialization when necessary
```

This sequence helps concentrate resources where they become genuinely useful.

---

## Open what needs to circulate.

Open source does not mean the absence of an economic model.

Not every layer of a system necessarily needs the same degree of openness.

Launchers, interfaces, examples, connectors or components designed to facilitate:

- experimentation;
- integration;
- interoperability;
- reproducibility;
- use;

may be opened when openness increases their usefulness.

Economic value can then develop around many dimensions:

- execution;
- measurement;
- scale;
- integration;
- availability;
- compliance;
- interpretation;
- operational use;
- services;
- responsibility;
- infrastructure required for scaling.

We are not anti-SaaS.

We are not anti-platform.

We are **anti-unnecessary complexity**.

---

## A fundamental measurement can support many uses.

NeoMundi develops a runtime measurement layer designed to observe certain behaviors of artificial intelligence systems.

A fundamental measurement does not need to be confused with every use that may derive from it.

Around the same measurement layer, many things can be built:

- launchers;
- workflows;
- reporting tools;
- visualizations;
- connectors;
- governance systems;
- scientific experiments;
- business tools;
- specialized infrastructure;
- articulations with third-party systems.

These objects may differ radically in size, purpose and sophistication.

Some may remain extremely small.

Others may eventually become significant industrial systems.

The purpose of Arte Povera Software is not to prevent this evolution.

It is to **avoid forcing it too early**.

---

## Launchers before a library of platforms.

A launcher is a particularly simple form of software.

It can:

- take a file;
- call a service;
- execute a sequence of actions;
- apply several parameters;
- produce a result.

Sometimes it can fit into only a few files.

That is precisely what makes it useful.

A launcher can make a function immediately testable without prematurely building an entire platform around it.

Several launchers may then reveal:

- recurring uses;
- shared components;
- common requirements;
- functions worth industrializing.

Architecture can therefore emerge from use rather than being completely dictated before use exists.

---

## Lightweight reporting.

The same principle applies to outputs.

A result does not necessarily require a permanent dashboard.

A lightweight library may transform data into:

```text
CSV
HTML
JSON
charts
tables
summaries
longitudinal comparisons
reports
```

When several Python scripts are enough to meet the need, they may be the correct solution.

If the use becomes recurring, collaborative or critical, a larger infrastructure can then be built.

## AI Periscope: a first artifact.

**NeoMundi AI Periscope v0.1.0** is a deliberately simple first materialization of this approach.

Its principle is minimal:

```text
Your dataset
      ↓
AI Periscope
      ↓
NeoMundi ControlTower

Your provider
      ↓

      ↓
```

The user chooses:

AI Periscope does not attempt to become another platform.

It only adds the path required between a user-defined experiment and the NeoMundi measurement layer.

No imposed dataset.

No imposed benchmark.

No imposed business protocol.

**Only what is missing to make the experiment possible.**

## Minimal infrastructure does not mean minimal ambition.

Our ambition is not small.

Our resources are concentrated.

Infrastructure can begin small while pursuing a significant ambition.

The role of an initial architecture is not to reproduce on day one the form it may take several years later.

Its role is to make the next step possible.

We therefore seek to build systems that are:

- simple enough to test;
- clear enough to understand;
- documented enough to reproduce;
- open enough to integrate when useful;
- robust enough to produce real observations;
- measurable enough to evolve based on evidence.

Industrialization comes when use justifies it.

---

## An architecture that can emerge.

Arte Povera Software is not an aesthetic of poor software.

It is not the search for the shortest possible code.

It is not a rejection of industrial engineering.

It is a discipline of progression.

It accepts that a system may begin as:

```text
a script
```

then become:

```text
a library
```

then:

```text
a service
```

and eventually:

```text
an infrastructure
```

if each transition responds to a real need.

Architecture therefore does not necessarily need to be fully known at the beginning.

Part of the architecture can emerge from the interaction between:

- measurement;
- use;
- users;
- constraints;
- evidence.
